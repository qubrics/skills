This is preparation only: no commands run, credentials accessed, profiles created, API calls made, mailbox content read, state changed or email sent.

The installed Sendmux guide is the setup authority; the CLI's `--help` is the other setup authority it names. Start CLI and SDK work in an isolated child process. In that child, clear all inherited `QUBRICS_API_KEY`, `SENDMUX_API_KEY`, `QUBRICS_ACCESS_TOKEN`, `SENDMUX_ACCESS_TOKEN`, `QUBRICS_PROFILE`, `SENDMUX_PROFILE`, `QUBRICS_BASE_URL` and `SENDMUX_BASE_URL` before selecting account A's connection. The parent's account B key, competing access token and unapproved endpoints must not reach the prepared calls. Load only the intended secret from the user's secret store, or use the intended saved profile with direct credentials unset. Never request a pasted key or print one.

Authorise the endpoint before transmitting any credential. The guide gives these connection-check endpoints: Management uses `GET https://app.sendmux.ai/api/v1/me`, Mailbox uses `GET https://app.sendmux.ai/api/v1/mailbox/connection`, and Sending uses `GET https://smtp.sendmux.ai/api/v1/me`. An inherited base URL is not authorised merely because it exists. Do not guess which legacy or renamed variable wins; remove both families of inherited overrides and establish the authorised endpoint first.

Prepare three separate branches; these are descriptions of the guide's sequence, not executed setup:

- **Raw root key:** obtain only A's `smx_root_` key from the secret store in the isolated child. The guide's `SENDMUX_API_KEY="$SENDMUX_ROOT_KEY" sendmux profiles:set root --default --json` stores it in the `root` profile. Subsequent profile calls must have direct credentials unset. Check `sendmux management:get-connection --profile root --json`, verify A's returned identity, then the guide's harmless Management example is `sendmux management:mailboxes:list --query limit=1 --profile root --json`. Keep this credential and client/profile separate from Mailbox access; a root key is not for mailbox-scoped examples.
- **Raw mailbox key:** obtain only A's intended `smx_mbx_` key from the secret store in a separately prepared child. The guide's `SENDMUX_API_KEY="$SENDMUX_MBX_KEY" sendmux profiles:set mailbox --default --json` stores it in the `mailbox` profile. With direct credentials unset, check `sendmux mailbox:get-connection --profile mailbox --json`, verify A and the intended authorised mailbox, then use `sendmux mailbox:me:get --profile mailbox --json` as the harmless subsequent call.
- **Existing authenticated profile:** reuse authorised profile `work`; create no profile. Keep direct credentials unset, including `SENDMUX_API_KEY`, `SENDMUX_ACCESS_TOKEN` and any `--api-key` argument, because the guide says these override profile selection. The initial isolation also removes the competing QUBRICS credentials, profile selectors and both base URLs. Use the relevant `management:get-connection`, `mailbox:get-connection` or `sending:get-connection` with `--profile work --json`, then keep that same profile and surface for the next call. For an existing OAuth profile, reuse its consented access; OAuth accesses an existing account, while `agent:register` creates a new agent inbox.

The explicit legacy `SENDMUX_API_KEY` assignments in the raw-key examples do not replace the isolation precondition. Setting that one variable alone leaves the parent's `QUBRICS_API_KEY`, competing access token and base URLs present. Use those examples only after clearing the full list and loading A's intended key; their spelling does not establish precedence over competing QUBRICS values. Profile creation stores the credential in the intended permission-restricted profile, and later profile calls must not carry the direct-key input forward.

For every branch, permission and intended identity are separate gates. Inspect the returned connection metadata against account A and the intended credential: `data.label` is the connection name, `data.team.id` the stable team identifier, and `data.mailboxes[].id` / `data.mailboxes[].email` identify authorised mailboxes when present. These checks need no mailbox selector and are metadata-only, not a message-content read or a separate mailbox-list operation. Explain the fields without displaying customer values when those values are not wanted. If the unisolated connection grants permission but identifies account B, stop and resolve the mismatch with the user before reading content, making a subsequent task call or mutating anything. If identity cannot be verified, stop in the same way. A successful connection check validates credential and surface; it does not establish Sending credits, provider readiness or mailbox storage.

The SDK snippets are subsequent calls after connection validation, using the same intended credential and surface. The Mailbox example uses `createMailboxClient` and `mailboxGetMe`; the Management example uses `createManagementClient` and `managementListMailboxes` with `limit: 1`. Apply the same child-process isolation and endpoint authorisation before supplying the key or running either example. The guide does not document SDK environment precedence or an endpoint-override implementation here, so do not invent code or assume that explicit `apiKey` defeats an inherited URL. Sending package/OpenAPI discovery is harmless discovery, not credential validation; do not send an email as a health check.

The guide's full-registration-revocation guarantee is precise: a full registration revoke removes read access, invite/recovery handles and every derived delegated sending token. The saved agent profile's durable credential normally allows reading and receiving mail without an expiry date while registration remains active; it does not authorise sending or message changes. Delegated Sending tokens become available only after the owner accepts the invitation and approves sending, and last one hour. Full revocation removes those derived tokens too. The guide does not say that full registration revocation deletes the accepted owner's association, so do not infer that it does.
