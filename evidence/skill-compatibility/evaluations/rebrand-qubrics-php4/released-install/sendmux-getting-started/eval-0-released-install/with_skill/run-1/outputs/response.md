# Guide-only preparation: Sendmux getting started

This explains `skills/sendmux-getting-started/SKILL.md` only. Neither the existing-account branch nor the keyless-registration branch has been executed.

## Existing account A: choose storage, then validate identity

The Safety first preference does not permit trusting inherited credentials. It prefers the intended permission-restricted CLI profile, or the intended credential from the user's secret store, after inherited overrides have been cleared in an isolated child process. Clear `QUBRICS_API_KEY`, `SENDMUX_API_KEY`, `QUBRICS_ACCESS_TOKEN`, `SENDMUX_ACCESS_TOKEN`, `QUBRICS_PROFILE`, `SENDMUX_PROFILE`, `QUBRICS_BASE_URL` and `SENDMUX_BASE_URL`. Then deliberately select A's profile or load only A's intended secret. Expected authorised profile/secret-store storage is not a leak; accidental inheritance is not authorisation. Never ask for a pasted key or print it, and keep it out of process arguments and output.

Use the authorised endpoint before any credential is transmitted. The parent QUBRICS key for B, competing SENDMUX token and unapproved base URLs must not enter the child examples. Supplying `SENDMUX_API_KEY` explicitly in a guide example does not itself remove a competing QUBRICS credential or endpoint. This guide requires isolation but does not specify a release/candidate QUBRICS precedence table; no such implementation is inferred here.

For a raw Management key, the guide prepares a separate root profile with secret-backed `SENDMUX_API_KEY="$SENDMUX_ROOT_KEY"` input to `sendmux profiles:set root --default --json`. For a raw Mailbox key, it similarly uses `SENDMUX_API_KEY="$SENDMUX_MBX_KEY"` with `sendmux profiles:set mailbox --default --json`. These are descriptions, not executed commands. Populate those source values from A's secret store inside the isolated process. Use `smx_root_` only for Management; use `smx_mbx_` or a scoped `smx_agent_` credential for Mailbox. Keep keys and clients/profiles separate. After profile creation, leave direct credentials unset before subsequent `--profile root` or `--profile mailbox` operations.

For an already authenticated API-key or OAuth profile `work`, create no profile: select that actual profile for both its connection check and the following call. Profile calls must not also carry `SENDMUX_API_KEY`, `SENDMUX_ACCESS_TOKEN` or `--api-key`, which take precedence over the profile; the initial clearing also removes their QUBRICS counterparts. OAuth authenticates an existing account; if login or consent is needed, route to `sendmux-cli` first rather than registering a new agent inbox.

Validate the selected surface before task work: `sending:get-connection --profile work --json`, `mailbox:get-connection --profile work --json` or `management:get-connection --profile work --json`. For newly created root/mailbox profiles, substitute those selected names. No mailbox selector is needed for these checks. The documented HTTP counterparts are `GET https://smtp.sendmux.ai/api/v1/me` for Sending, `GET https://app.sendmux.ai/api/v1/mailbox/connection` for Mailbox and `GET https://app.sendmux.ai/api/v1/me` for Management.

Explain the returned metadata without displaying customer values unnecessarily: `data.label` names the connection; `data.team.id` is its stable team ID; `data.mailboxes[].id` and `.email` identify authorised mailboxes when present. Match identity and any authorised mailbox selection to A and the intended credential. A check granting permission but identifying B is a stop before mailbox content, sending, mutations or other task work. Resolve the mismatch with the user, then validate the intended selection. Do not pass a wrong-account success forward as verified setup or hand it off as an authorised A connection.

These checks are metadata-only and do not require a separate mailbox-list operation. Sending's check needs `email.send`; Management and Mailbox need their respective surface access without an additional read permission. Success does not establish credits, provider readiness or mailbox storage. Public OpenAPI discovery does not validate credentials.

## Later SDK and first-call examples

For application code, the guide uses the package matching the selected surface: `@sendmux/mailbox`, `@sendmux/management` or `@sendmux/sending`. Its examples create the corresponding client with explicit `apiKey: process.env.SENDMUX_API_KEY!`. That explicit key is not proof that an inherited endpoint is authorised. Apply the same isolated-process clearing first, load the intended key, ensure the authorised endpoint and validate the same credential/surface identity before the SDK's later task call. The guide does not give an SDK base-URL option or exact SDK connection-check implementation, so neither is invented here.

After validated Mailbox setup, the harmless identity call is `mailbox_get_me`, CLI `mailbox:me:get`, or SDK `mailboxGetMe`. After Management validation, the guide's small mailbox-list example uses `management_list_mailboxes`, CLI `management:mailboxes:list` or SDK `managementListMailboxes` with limit 1; OAuth additionally needs `mailbox.admin.read` for that list. Sending uses `sending:get-connection` for credential validation; the OpenAPI example is discovery only. Do not send a real email as a health check. Real sends route to `sendmux-send-email` with explicit message details and an `Idempotency-Key`.

## Separate case: no account, key or profile

The guide documents keyless agent self-registration and requires identifying the installed Sendmux skill and CLI `--help` as setup authority before giving registration steps. This creates a new agent inbox; it does not authenticate account A. No existing account, API key, challenge or proof-of-work step is required.

In this branch, registration necessarily happens before the new profile can be identity-checked. The documented sequence is to install the CLI if needed, then use `agent:register` for a named durable profile with `--mailbox-local-part`, `--client-name`, optional `--default` and `--json`. The CLI saves idempotency state before registration, stores the returned credential in its restricted local profile without printing it, and waits up to 10 minutes for readiness. Repeating the same profile and options resumes safely. Never copy its credential to chat, logs, prompts, screenshots or repository files.

Next validate the saved profile with `mailbox:get-connection --profile my-agent --json`, verify its returned identity and authorised mailbox, then use `mailbox:me:get --profile my-agent --json` as the harmless first mailbox call. No content access, sending, other task work or identity-verified handoff should precede successful validation. If another worker receives a setup handoff, it must retain this pending verification gate rather than treat registration alone as permission to continue. Invite the owner with `--owner-email` during registration or `agent:invite-owner` later.

The saved agent profile can read and receive email without an expiry date while registration remains active. Its durable credential does not authorise sending or message changes. Sending remains unavailable until the owner accepts and approves it; after that, `sending:*` automatically obtains a one-hour `email.send` delegated token and caches it until near expiry. The inbox is capped at 500 MiB before approval; owner-approved sending first raises it to at least 5 GiB. Revoking sending alone does not alter current storage allocation.

The guide's full-registration-revocation guarantee is exactly that it removes read access, invite/recovery handles and every derived delegated sending token. It does not say that revocation deletes the accepted owner's association; that must not be inferred.

No setup command, credential access, connection check, SDK call, mailbox read, mutation, send or publication occurred. This is guide-derived preparation, not live identity, installed-client or delivery certification.
