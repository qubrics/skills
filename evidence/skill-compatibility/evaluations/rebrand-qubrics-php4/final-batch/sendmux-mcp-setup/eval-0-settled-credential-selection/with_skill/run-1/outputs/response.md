This is preparation only. Start both local servers and their clients in isolated child processes. Clear inherited generic and per-surface API keys, HTTP bearer tokens, API base-URL, transport and surface-selection overrides under both `QUBRICS_` and `SENDMUX_`; then load only intended values from the user's secret store. `QUBRICS_` values precede their `SENDMUX_` fallbacks, and a per-surface key can override a generic key. Therefore setting the intended `SENDMUX_API_KEY` alone does not protect `mbx_support` from the parent's different `QUBRICS_MAILBOX_API_KEY`. Remove that competing input as part of isolation. Keep credentials out of arguments, output and checked-in configuration, and use only the authorised upstream endpoint before transmitting them.

For **Mailbox-only**, the planned local stdio process is `sendmux-mcp-mailbox` with only A's intended mailbox credential supplied through the clean environment. Mailbox accepts `smx_mbx_` or an appropriately scoped `smx_agent_`, never a root key. For **combined** `sendmux-mcp`, explicitly select only the authorised surfaces and independently supply their intended credentials: `SENDMUX_MAILBOX_API_KEY` for Mailbox, `SENDMUX_MANAGEMENT_API_KEY` for Management and `SENDMUX_SENDING_API_KEY` for Sending, or the corresponding intended `QUBRICS_` values. Management requires `smx_root_`; Sending requires send-capable `smx_mbx_` or owner-approved Sending-resource `smx_agent_`. A generic key is not a substitute for distinct correctly scoped credentials across all three surfaces.

All documented combined-server surface selectors, in precedence order, are `--surfaces`, `--surface`, `QUBRICS_MCP_SURFACES`, then `SENDMUX_MCP_SURFACES`. Use an explicit authorised choice after clearing inherited selectors. Transport and API endpoint overrides must likewise be cleared before the desired stdio or local/private HTTP setup is chosen. The guide's HTTP example explicitly uses `--transport http --host 127.0.0.1 --port 8765 --path /mcp`; `/health` reports selected surfaces but does not validate upstream identity.

Local/private HTTP has two separate credentials: the upstream Sendmux API key in the server environment, and the client's `Authorization: Bearer ...` using `SENDMUX_MCP_HTTP_BEARER_TOKEN` to protect the local MCP endpoint. Supply that token secret-safely, not as a literal argv value. Hosted OAuth instead uses `https://mcp.sendmux.ai/mcp` with no API key; a REST OAuth access token is not its bearer. For an existing CLI profile such as `work`, prefer the durable CLI profile for terminal work; do not extract its credential merely to force local MCP. Hosted MCP requires its separate authorisation.
