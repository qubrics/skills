Then load only the intended key from the user's secret store, or select an existing profile with direct credentials unset. Use the authorised endpoint before transmitting credentials. Keep secrets out of argv, output and chat. The guide's legacy `SENDMUX_API_KEY` assignments are examples **after** this isolation; assigning that variable alone in the supplied parent environment is insufficient because competing credentials and endpoint overrides remain.

Prepared raw-key branches, without creating anything:

- Root: privately supply A's `smx_root_` key as `SENDMUX_API_KEY` for `profiles:set root --default --json`; subsequent profile calls leave direct credentials unset. Plan `management:get-connection --profile root --json`, then, only after identity verification, `management:mailboxes:list --query limit=1 --profile root --json`. The later list needs its operation permission, including `mailbox.admin.read` for OAuth.
- Mailbox: separately supply A's `smx_mbx_` key for `profiles:set mailbox --default --json`; then unset direct credentials for `mailbox:get-connection --profile mailbox --json`. After identity verification and authorised mailbox selection, the harmless first call is `mailbox:me:get --profile mailbox --json`. Keep root and mailbox credentials in separate profiles/clients; a root key does not belong in mailbox examples.
- Existing authenticated profile: reuse `work` with `--profile work` for both the surface's connection check and later call. No login, profile creation, new API key or agent registration is needed. Skipping setup does not skip environment isolation or identity verification.
